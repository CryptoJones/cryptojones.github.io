Local Security RAG + Exploit-Dev Pipeline

A fully self-hosted, GPU-split retrieval-augmented-generation stack for security research — no cloud, no API keys leaving the LAN. A ~488-PDF security library is embedded into a hybrid Qdrant index, cross-encoder reranked, and answered by an uncensored local model with real citations. Everything runs on a Tesla P100 + RTX 3060, with a 32 GB Radeon Pro V620 specialist tier landing on a second node.

What changed — the 2026-08-13/14 rebuild

The Tesla P100 (16 GB HBM2) is now physically installed on pluto, replacing the GTX 1080. That single swap rewrote the whole stack: the embedder went from ~5–11 chunks/s to full-rate FP16, the reranker finally has a home, and the box now hosts a 35B model entirely in VRAM. Along the way the design shifted from an agentic “orchestrator routes to specialist” model to a direct grounded-RAG pipeline — because PrivateGPT v2 turned agentic and orphaned the bulk-ingested corpus (see Grounding, the hard way). Net result: grounded security-corpus chat actually works end-to-end, served through a browser UI on the LAN.

How a query flows LIVE

A single service — rag-proxy on :8092 — speaks the OpenAI chat API as one model id, security-corpus, and drives the whole pipeline. That means the existing web chat UI and the model-swap proxy treat grounded RAG like any other model: pick it from a dropdown.

  1. Analyst query arrives at rag-proxy (:8092) via the LAN-only /chat/ web UI — nginx reverse-proxy, RFC-1918 gated.
  2. The query is embedded two ways in parallel: dense via Qwen3-Embedding-0.6B (through embed-clamp, :8085) and sparse BM25 (:8086).
  3. Qdrant runs a hybrid query — dense + sparse prefetch, fused with Reciprocal Rank Fusion — returning the top 32 candidate chunks.
  4. The 32 candidates go to bge-reranker-v2-m3 (:8088), a cross-encoder that re-scores each (query, chunk) pair and keeps the best 5.
  5. Those 5 chunks are assembled into a grounding prompt with numbered sources and a “answer only from these sources” instruction.
  6. huihui-Qwen3-30B-A3B-abliterated (:8083) streams the answer; rag-proxy appends a real Sources list of the actual file names.

Every stage is fail-open: if sparse or the reranker is down, retrieval degrades to dense-only / raw order rather than erroring. Verified end-to-end against the real corpus — answers cite actual books (Shellcoder’s Handbook, CEH v9, the XSS Attacks title), not hallucinated titles.

The corpus

~488 PDFs — a security/tech library of audit references and exploit-dev material — flow through marker into clean Markdown, get chunked, embedded, and indexed in Qdrant as 143,193 hybrid (dense + sparse) points. The model never “memorizes” the books; it retrieves the relevant pages at query time and answers grounded in them, with citations. Direct retrieval scores sit at a healthy 0.64–0.67 cosine; the reranker then pulls the genuinely-relevant chunk from #14 up to #1 where a limited context window can see it.

Grounding, the hard way — when the corpus goes invisible

The single most instructive failure of the rebuild: the RAG chat gave confident, well-written answers — that cited books not in the library. It was hallucinating grounding. The diagnosis chain is worth keeping.

  1. A great answer with a fake citation is worse than an error. The tell was a citation to a plausible-sounding title that wasn’t in the corpus. If retrieval were working, every citation would be a real file name. Always verify grounding against the known source set, not against how confident the prose sounds.
  2. “RAG is running” ≠ “RAG is grounding.” The reranker service was up and healthy but receiving zero requests during chat — it was serving nothing. A component being alive says nothing about whether it’s in the path.
  3. PrivateGPT v2 went agentic and per-artifact. It no longer chats over “all your docs”; retrieval is a semantic_search tool the model must choose to call, and that tool refuses to run without an ingested-artifact context. The bulk-ingested corpus predates that model — /v1/artifacts/list returned 0 artifacts. The 143k vectors existed and queried perfectly, but were orphaned from the chat path. The vectors were never the problem; the framework’s idea of “a searchable thing” had changed underneath them.
  4. The model wasn’t the problem either. Forcing the tool still produced no call — but the same model, hit directly, emitted a clean tool call on the first try. The tool definition simply wasn’t being sent, because there was no artifact to attach it to.
  5. The fix was to stop fighting the framework. Rather than re-ingest 488 PDFs through the new artifact API (hours, and a re-run of the 8×-duplication risk below), a ~230-line proxy does the pipeline directly — embed, hybrid-search, rerank, ground, stream — and presents as one OpenAI model so the existing UI just works. When the tool a framework hands you has outgrown your use case, a thin purpose-built endpoint beats bending the framework back.
  6. Block-buffered stderr hides the truth. Instrumenting the proxy showed nothing until it was run with python -u — the “0 logged ≠ stuck” gotcha, again. Unbuffered, it printed retrieve: hybrid(dense+sparse) and rerank OK: 30→5, proving the path end-to-end.

The P100 install — a GPU swap breaks more than you think

Dropping a passively-cooled datacenter card into a consumer tower surfaced a cluster of gotchas, each masquerading as something else.

  1. “Won’t POST” was a BIOS toggle. The board hung before video because CSM was enabled, which greys out Above-4G Decoding — and without Above-4G the P100’s 16 GB BAR can’t be mapped. They’re coupled: CSM off first, then Above-4G becomes settable. The headless box was diagnosed remotely by watching the UniFi controller for the machine’s Wi-Fi MAC re-associating — a network controller doubles as a boot sensor when there’s no monitor.
  2. Same-generation, different kernel. The P100 is GP100 = sm_60; the retired GTX 1080 was GP104 = sm_61. Every local llama.cpp build targeted 61;86 and died on the P100 with no kernel image is available for execution on the device — it allocates VRAM fine, then fails at first kernel launch. Rebuilt with -DCMAKE_CUDA_ARCHITECTURES="60;61;86". (CUDA 13 dropped Pascal entirely, so this pins to CUDA 12.9.)
  3. The card throttled to 45% clock — and it was a fan curve, not cooling. Under load the P100 hit 80 °C in under a minute and clocked from 1328 to 594 MHz. It had a blower. The blower was on a chassis fan header whose curve tracks CPU temperature — and the CPU sits on a cold AIO, so the board idled the fan at ~30% while the GPU cooked. Nothing in the loop knew the GPU existed. Pinning the header to 100% dropped peak-load temp 80 → 60 °C and held full boost indefinitely. Lesson: any passive datacenter GPU in a consumer board has an open control loop — wire its fan to constant 12 V, never a temp-driven header.
  4. The swap silently broke every service that named the old card. Scripts using a numeric CUDA_VISIBLE_DEVICES=1 kept pointing at “device 1” — which used to be the 1080 and was now the P100 — and services sized for the 1080’s 8 GB OOMed on the P100. Numeric indices silently retarget when hardware moves; pin by GPU-UUID instead.

Lessons learned — getting a code-heavy corpus through a fixed-context embedder

Backfilling the security/programming library surfaced a set of non-obvious gotchas about local embeddings. The fix that fell out — a transparent, token-aware embedding proxy — is open-sourced as embed-clamp.

  1. A batch of embeddings shares one context budget. With the client batching ~10 chunks per request, the server returned request (17821 tokens) exceeds the available context size (8192 tokens) — even though each chunk fit on its own. llama.cpp counts the whole batch against n_ctx. Your effective per-input budget is n_ctx / batch_size, not n_ctx; batch size 1 is the safe default when inputs run near the limit.
  2. The real wall is atomic chunks, not batching. Single unbroken blocks — code listings, opcode tables, hex dumps — reached 22k–30k tokens. No batch or context setting helps: an 8 GB embedding card can't hold a 30k-token sequence, and the chunker won't break the block.
  3. RAG chunkers treat code/tables as atomic and bypass the token splitter. “Markdown-aware” parsers split on headings/sentences and token-limit the pieces — except tables (parsed to dataframes) and fenced code are emitted as single atomic nodes that skip the splitter entirely. The token limit you think you set never applies to exactly the blocks that overflow.
  4. Re-splitting markdown at the source is fragile. Re-wrapping a giant code block into smaller fenced blocks desyncs any parser that toggles on ``` lines — code content often contains backtick runs. Always verify-or-revert: re-segment the output and restore the original if any block is still over the ceiling. Never leave a document worse than you found it.
  5. The robust fix lives at the embedding boundary, not the chunker. Rather than chase every atomic-node bypass path, put a proxy in front of the embedder: pass normal inputs through byte-identical, and for oversized ones split → embed pieces → pool into one vector — model- and pipeline-agnostic, no source mangling. Keep pass-through exact (cosine ≈ 1.0), give the embedding client a long timeout (pooling = several sequential embeds), and don't tokenize per line — calibrate a char budget so the GPU stays the bottleneck. (That tool is embed-clamp.)
  6. Operational gotchas. Don't poll the vector DB under heavy ingest load — counts time out and read inconsistently, and each poll adds load; trust total-point growth or the run’s summary line instead. exact:false counts over-report. Block-buffered stdout hides progress (“0 logged” ≠ stuck). And a client-side timeout isn’t data loss — a server that streams vectors as it embeds may finish a request the client already abandoned.

Lessons learned — recovering a corrupted ingest (the 8× duplication)

A second backfill pass went wrong in an instructive way: an unattended ingest loop quietly re-embedded the same books over and over until Qdrant held ~1.74M vectors for ~250 documents — a median of ~7,000 points per book, the worst at 35,724. Pulling that apart surfaced a different class of gotcha than the embedder ones above — idempotency, runaway processes, and old-GPU limits.

  1. Idempotency has to be against the store, not your own bookkeeping. The ingester deleted a document’s old vectors only when it was already in the local manifest. A doc that succeeded server-side but whose client call timed out got recorded as failed — so the next retry wave re-ingested it without deleting first, appending a second full copy. Across ~40 waves that compounded to 8×. Fix: purge-before-ingest unconditionally (delete the artifact’s vectors every time — a cheap no-op when absent), and cap retries with a quarantine so a doc that simply can’t ingest stops being re-chunked forever.
  2. Detached children outlive the parent you killed. The loops were launched with setsid, so killing the orchestrator left the ingest driver (and its worker grandchildren) running — three separate escaped loops over one session, each still duplicating. Always pgrep for stray drivers before and after any rebuild step; a dead parent is not a stopped job.
  3. You can’t cheaply de-duplicate re-ingests. The duplicate vectors weren’t byte-identical copies — the source .md had been re-split between runs, so chunk boundaries drifted and the “duplicates” were distinct vectors (32,981 points / 31,124 unique on one book). Nothing to delete cheaply; the only correct fix is wipe the collection and re-embed from the current text.
  4. Pascal is the wall. The interim embedder ran f16 on a GTX 1080 (Pascal, sm_61) at ~5–11 chunks/s, and batching did nothing — llama.cpp serialized the batch and Pascal’s f16 rate is ~1/64. Worse, the modern stack has dropped Pascal: vLLM/TEI won’t run on sm_61, and marker’s Torch (cu130) has no Pascal kernels at all (no kernel image is available for execution on the device) — so you can’t even shard the PDF→Markdown sweep onto that card. The same model on the Ampere RTX 3060 hits ~27 chunks/s and does scale with batch. Confirm a card can run your kernels before you plan around it. (Since resolved: the P100’s full-rate FP16 removes this wall for the embedder.)
  5. The real speed lever is a properly-batching backend. llama.cpp’s embedding endpoint is effectively one-sequence-at-a-time; swapping to vLLM serving the same Qwen3-Embedding on the Ampere card — with requests actually batched on-GPU — is what turns a ~day-long re-embed into a few hours.
  6. Trust the measurement, not the process. The bloated collection looked healthy by every process check; only counting points-per-document revealed the 8×. Gate “done” on an audit — each doc’s point count near its real node count (none at a multiple), a sane total, and a vector-hash duplicate scan — and start every rebuild from an empty collection with the manifest reset (wipe without resetting the manifest and the ingester skips everything, leaving you empty).
