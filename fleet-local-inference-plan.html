GPU Inference Cluster Hardware Plan 2026-06-12

Created: 2026-06-12
#hardware#gpu#node-b#llm-inference#homelab

Summary

Final plan for placing the P100 (16GB), RTX 3060 (12GB) and Radeon Pro V620 (32GB) across machines. Key constraint: node-b's Gigabyte B85-HD3 (2014 BIOS) has NO Above 4G Decoding, so it cannot host either big-VRAM card — fix is a Supermicro X10SLH-F board swap (~$67 new) that reuses the i5-4670K + DDR3.

Card placement (final)

B550 box — ASRock B550 Phantom Gaming 4, Ryzen 5 5600X (NO iGPU), modern BIOS w/ Above 4G + ReBAR:

  • RTX 3060 (12GB) → PCIE2, the x16 CPU slot. It is the ONLY display-capable card (5600X has no iGPU), so it must stay here; tty1/console lands on it cleanly.
  • Tesla P100 (16GB) → PCIE4, the x4 chipset slot (only x4 wired; verified via LnkSta "Width x4 downgraded"). Just pull the existing GTX 1080 and drop the P100 in — do NOT move the 3060.
  • All-NVIDIA/CUDA → can pool 3060+P100 to ~28GB (pooling crosses the x4 link, so modest penalty). x4 only costs the P100 a few seconds of model-load time; single-card inference is unaffected.
  • Enable Above 4G Decoding + Re-Size BAR in BIOS (required for the P100's 16GB BAR).

node-b — currently Gigabyte B85-HD3, i5-4670K, 32GB DDR3-1600 non-ECC (4x8GB Crucial Ballistix), GTX 1060 6GB:

  • DEAD END for big-VRAM cards. B85-HD3 F2 BIOS (2014) has NO "Above 4G Decoding" — proven empirically: zero PCIe MMIO window above 4GB (all BARs crammed in e0000000-feafffff; highest iomem addr is just top-of-RAM). No official BIOS past F2 adds it; no working modded BIOS exists.
  • P100 (fixed 16GB BAR) CANNOT work here, period. V620 (32GB BAR) also won't unless it falls back to a small 256MB BAR without ReBAR (RDNA2 can in theory; cloud firmware unknown — untested).

THE PLAN: rackmount node-b + swap the motherboard.

  • New board: Supermicro X10SLH-F (Intel C226, LGA1150, mATX). ~$67 NEW at Unix Surplus.
  • Reuses the i5-4670K and all 32GB DDR3-1600 non-ECC verbatim (board takes "up to 32GB DDR3 Unbuffered ECC/Non-ECC 1600").
  • Has Above 4G Decoding (confirmed in Supermicro X10 C226 BIOS manuals: Advanced > PCIe/PCI/PnP Configuration > Above 4G Decoding, Enabled/Disabled).
  • IPMI/BMC gives remote console + power (better than iGPU for a headless rack node; video is via the ASPEED BMC, not the Haswell iGPU). The HD4600 iGPU still usable as GPGPU/QuickSync.
  • V620 (32GB) → its PCIe 3.0 x16 slot at FULL x16 (single CPU-lane slot, won't drop to x8). Run under ROCm (gfx1030, Ubuntu 24.04).
  • Alt board if literal monitor outputs wanted instead of IPMI: Supermicro X10SAE (C226, ATX, true iGPU video DP/HDMI/DVI/VGA), ~$100-180 used.

Per-card gotchas

  • P100 AND V620 both use an EPS-style 8-pin power connector (NOT PCIe 6+2 — plugging PCIe in can fry them).
  • Both are passively cooled datacenter cards → need forced airflow (blower/shroud/duct).
  • P100 = 250W, V620 = ~300W → 650W+ quality PSU in each host.

End state

  • B550 box = CUDA node: 3060 + P100, ~28GB pooled.
  • New X10SLH-F box (rackmounted node-b guts) = ROCm node: V620, 32GB at x16.
  • GTX 1060 retired or repurposed; GTX 1080 pulled from the B550 box.

Reality check

At $67 for the X10SLH-F, reusing the 4670K + DDR3 beats a new AM4 5600G/DDR4 build on price while gaining IPMI. (The DDR4 5600G build was only ever the rejected alternative.)

Wiring — two steps

1. Add a named provider per endpoint (base_url + model alias + placeholder api_key; llama-server is keyless on the LAN). Illustrative:

hermes config.yaml (illustrative)
# ILLUSTRATIVE — verify keys against the live hermes config
providers:
  node-a-agent:       { base_url: http://node-a:8081/v1,  model: qwen3-abliterated-30b, api_key: none }
  node-b-coder:     { base_url: http://node-b:8080/v1, model: qwen3.6-27b-coder,    api_key: none }
  openrouter-vision: { base_url: https://openrouter.ai/api/v1, model: <vl-model>, api_key: $OPENROUTER_KEY }

2. Map hermes role slots (primary / auxiliary / delegation) to the provider names:

  • primary + delegation / tool work → node-a-agent (fast MoE, tool-calling; the always-on default)
  • coding tasks → node-b-coder (dedicated slot or routed sub-agent/tool, depending on how hermes dispatches code work)
  • vision / image tasks → openrouter-vision

Gotchas (pre-loaded)

  • A bare provider: does NOT route — it needs a named providers: entry (the lesson from ollama). See [[node-a-hermes-ollama]].
  • Use LAN-resolvable hostnames (node-a/node-b) or the the internal LAN IPs. hermes runs ON node-a, so node-a:8081 is a local hop, node-b:8080 is one LAN hop.
  • Keep node-a's server --jinja so it emits proper tool_calls.
  • llama-server is keyless → the provider api_key only needs a non-empty placeholder.
  • Give the coder slot a sane timeout/fallback so a coding call doesn't hang the agent if node-b's server is mid-restart (e.g., after a model swap).
  • Ports: node-a MoE :8081, node-b coder :8080 — different boxes, no conflict.

Do when the hardware is in place

  • Read the live hermes config on node-a; confirm the real schema + file location.
  • Add the three named providers.
  • Map the role slots → providers.
  • Validate end-to-end: a tool-calling turn lands on node-a, a coding task on node-b, a vision task on OpenRouter; confirm the coder-slot timeout/fallback behaves.

Local Coding LLM on V620 — Model Choice + llama.cpp Prestage 2026-06-12

Created: 2026-06-12
#llm-inference#gpu#node-b#llama-cpp#rocm#homelab#fleet

Summary

RE-EVALUATED 2026-06-14: the V620 (32GB ROCm) always-on coding-node pick is now Qwen3.6-27B (dense) — unsloth MTP GGUF, UD-Q5_K_XL (20.35 GB). It beats the prior Qwen3.6-35B-A3B pick on coding (SWE-bench Verified 77.2 vs 73.4) and MTP speculative decoding (1.4–2.2× faster) cancels the dense speed penalty. DOWNLOADED + byte-size-verified on node-b 2026-06-14; the 35B-A3B GGUFs are kept as the throughput fallback. Fleet context: [[Homelab LLM fleet roles — node-a + node-b (always-on)]].

Decision (re-evaluated 2026-06-14)

Pick: Qwen3.6-27B (DENSE — hybrid Gated DeltaNet + Gated Attention, 64 layers, 262K native ctx, Apache-2.0).

  • GGUF: unsloth/Qwen3.6-27B-MTP-GGUF, variant UD-Q5_K_XL (20.35 GB) — fits the 32GB V620 with ~11GB headroom for KV/context. Max-quality alt: UD-Q6_K_XL (~26GB); more-context alt: UD-Q4_K_XL (~17.9GB).
  • Why it now beats the old Qwen3.6-35B-A3B pick:
    • Coding quality: SWE-bench Verified 77.2 vs 35B-A3B 73.4 (official Qwen table; the 27B even edges Qwen3.5-397B-A17B's 76.2). Also Terminal-Bench 2.0 59.3, SWE-bench Pro 53.5. Dense beats MoE when full-parameter engagement matters for multi-file reasoning.
    • Speed parity via MTP: Qwen3.6-27B is trained with Multi-Token Prediction; the MTP GGUF + --spec-type draft-mtp yields 1.4–2.2× faster generation with no accuracy change — this cancels the dense-vs-MoE throughput gap that originally favored the A3B MoE.
  • Sampling (coding / thinking mode): temperature=0.6, top_p=0.95, top_k=20, min_p=0.0. Qwen3.6 runs in thinking mode by default (<think>…</think>).
  • Bonus: Qwen3.6-27B has a vision encoder (multimodal) — NOT needed (vision is outsourced to cloud/OpenRouter per CJ) but available if ever wanted (needs the mmproj projector + a llama-mtmd build).

Prestage status on node-b (VERIFIED 2026-06-14 via SSH)

cd ~/llama.cpp && git pull
cmake -B build-rocm -DGGML_HIP=ON -DAMDGPU_TARGETS=gfx1030 -DLLAMA_CURL=ON -DCMAKE_BUILD_TYPE=Release

  --spec-type draft-mtp --spec-draft-n-max 2 \
  --temp 0.6 --top-p 0.95 --top-k 20 \

The MTP draft head is embedded in this MTP GGUF, so --spec-type draft-mtp works with the local -m file (no -hf pull needed — it's already downloaded). Frontier model eval 2026-06-16 — Kimi K2.7, Nex-N2-Pro & Nex-N2-mini vs the homelab fleet

Created: 2026-06-16
#llm-inference#gpu#node-b#v620#rag#fleet#homelab#model-eval#kimi#nex-n2#moe#reference

Summary

Evaluated 2026-06-16 against the fleet's VRAM ceiling (32GB V620 / ~28GB post-P100 node-a pool). Kimi K2.7 (Moonshot, 1.04T/32B MoE) and Nex-N2-Pro (Nex AGI, 397B/17B MoE, Qwen3.5-based) are frontier agentic-coding models but NEITHER is fleet-hostable — they need hundreds of GB (Kimi ~577GB INT4, Nex-Pro ~145–794GB), so they're cloud/API-only (OpenRouter/SiliconFlow). The find: Nex-N2-mini (35B-A3B MoE, ~3B active, Qwen3.5-35B-A3B base, Apache-2.0, native tool-calling, 262K ctx) DOES fit a single 32GB V620 at Q4/Q5 GGUF (~19–27GB; full 256K+vision fits a 32GB card). Local V620 pick stays Qwen3.6-27B dense for raw coding; Nex-N2-mini is the faster, tool-native MoE alternative worth a head-to-head.

The two big ones — cloud/API only, NOT fleet-hostable

  • Kimi K2.7 (Moonshot, June 2026): MoE 1.04T total / 32B active, 256K ctx, multimodal (text+image; +video on Code pkg), always-thinking, native agentic, Modified-MIT open weights. SWE-bench Verified ~65.8 (K2 paper; K2.7-Code is coding-tuned, likely higher, no clean number found). VRAM ~2,308GB FP16 / ~1,154 INT8 / ~577 INT4 → 8×H100-class. API: OpenRouter kimi-k2.7-code ~$0.73/$3.49. No verified uncensored variant.
  • Nex-N2-Pro (Nex AGI, dropped 2026-06-02): MoE 397B total / 17B active, post-trained on Qwen3.5-397B-A17B, 262K ctx, multimodal, native function-calling + structured outputs, Apache-2.0. HF-card benchmarks: SWE-bench Verified 80.8, Terminal-Bench 2.1 75.3, SWE-bench Pro 58.8, GPQA-Diamond 90.7, IFEval 94.0, BrowseComp 83.7 — peer to GPT-5.5 / Claude Opus 4.7 on coding; beats DeepSeek-V4-Pro (1.6T) at a quarter the size. VRAM ~794GB full / ~145GB INT4 ("reaped" fits 2× DGX-Spark, barely). Free on OpenRouter + SiliconFlow during launch.
  • Fleet verdict: both far exceed 32GB (V620) and ~28GB (node-a pool) — off-box. Only realistic use = a cloud API burst for heavy agentic coding (like vision→OpenRouter today). Do NOT use as the local RAG generator: breaks the "fully local, nothing leaves the host, no per-token cost" principle of the node-a PrivateGPT stack, and neither is uncensored.

The actually-local one — Nex-N2-mini (the real takeaway)

  • MoE 35B total / ~3B active (8 of 256 routed experts + 1 shared), built on Qwen3.5-35B-A3B-Base, qwen35moe = hybrid linear-attention MoE (3 of every 4 layers Gated DeltaNet linear-attn, every 4th full-attn → only ~10/40 layers carry full-attn KV, so KV cache stays tiny). 40 layers, 262K train ctx, Apache-2.0, optional vision (mmproj ~0.9GB), ships a chat_template.jinja (native tool-calling — unlike Gemma).
  • GGUF: abundant already — bartowski, unsloth-style UD dynamic quants, and NVFP4 (Blackwell). Sizes: Q3_K_XL ~17GB · IQ4_XS ~18.8GB · Q4_K_M ~21.4GB · UD-Q4_K_XL ~22GB · UD-Q5_K_XL ~27GB · UD-Q6_K_XL ~32GB · Q8_0 ~36.9GB. Spheron VRAM est (4K ctx, b1): INT4 ~19GB / INT8 ~38GB / FP16 ~77GB.
  • Fits the 32GB V620 cleanly: Q4 (~19–22GB) leaves ~10GB for KV/context; one report runs the full 256K ctx + vision on a single 32GB card (RTX 5090) thanks to the small hybrid-linear KV. UD-Q5_K_XL (~27GB) fits with less headroom; Q6 (~32GB) too tight for usable KV.
  • Caveats: no MTP draft head in current GGUFs (block_count=40, nextn_predict_layers=0) → no MTP speculative decode (the Qwen3.6-27B MTP build has it). Still fast (3B active). MoE on node-b is fine here since it fits fully in VRAM at Q4 (no CPU-offload needed — node-b can't offload well off its DDR3/HDD).
  • Quality hint: GDPval ~1402 ≈ Qwen3.6-27B's ~1404, but tuned toward coding/agentic over broad capability.

V620 (node-b coding node) recommendation — updated

  • Raw coding quality / multi-file reasoning: keep the pre-staged Qwen3.6-27B dense (UD-Q5_K_XL, SWE-bench 77.2, MTP 1.4–2.2× speed, already downloaded + byte-verified). Still the default. See [[Local Coding LLM on V620 — Model Choice + llama.cpp Prestage 2026-06-12]].
  • Agentic / tool-heavy coding, max speed, native tool-calling: Nex-N2-mini is a strong contender — 3B-active MoE (fast without MTP), ships a tool template (fixes the tool-call fragility hit with Dolphin/Gemma), Apache-2.0, fits 32GB with full 262K ctx, gfx1030/ROCm via llama.cpp HIP (same build path as the Qwen pick). Worth a head-to-head once the V620 is installed.
  • Bonus (RAG angle): Nex-N2-mini's native tool-calling + 35B-A3B fit make it a candidate to replace the 8B Dolphin as the RAG generator on the post-P100 ~28GB node-a pool — bigger, agentic, tool-native — addressing the "small-model tool-calling is chatty" gap.
